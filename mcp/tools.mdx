Every MCP tool is a thin wrapper around a public API endpoint, and each tool's tier is the tier of the endpoint behind it. There is no clean split by family: among the single-trader tools the lifecycle and compare tools are Starter and the drawdown curve is Pro; most HIP-4 tools are Free, with some at Starter and two at Pro; the live snapshot tools (cohort bias, liquidation heatmap, risk overview and coin snapshot, recent liquidations and their summary) are Starter while live history and the chart-layer tools are Pro, and `live_long_short_ratio` is Free; `market_price` and `market_orderbook` are Free, `market_recent_candles` is Starter and `market_historical_oi` is Pro; `book_summary` is Starter and the other book tools, including the trigger-order tools, are Pro; the four Sharpe tools are Starter; the archetype tools are split between Starter and Pro. Where a tier cell below links to the matrix, check the matrix for that tool's current tier. Check [the tier matrix](/api-reference/tiers) for the endpoint a tool wraps rather than inferring from its name.

The connector registers **115 tools**; `builder_heatmap` is withheld while its hourly rollup backfills, so clients see 114.

Every tool reads from a public API endpoint, so the [API reference](/api-reference/introduction) is where the response fields live. The **inputs are not always the endpoint's**: several tools accept shaping parameters the route itself does not take — see [Connector-side parameters](#connector-side-parameters). As of **v0.12.0** the catalog includes the [L4 order book](#l4-order-book-v0-12-0): four `book_*` tools answering a question each, rather than handing you a raw book to parse. v0.11.0 added [builder analytics](/api-reference/builders): eleven `builder_*` tools covering the leaderboard, per-builder profiles, attributed traders and fills, cohort composition, retention, audience overlap, user lifecycle, journey economics and order intent, plus the inverse per-wallet view.

## Sharpe ratios (v0.17.3)

All four Sharpe tools are **Starter**. An annualized **realized-PnL Sharpe** — √365 × mean daily realized PnL ÷ its sample standard deviation, days without fills counted as zero, today excluded. It is a proxy, not a portfolio Sharpe: not divided by equity, and fees, funding and unrealized PnL are left out. It rewards consistency over size, so read it next to `realizedPnl`. See [Sharpe ratios](/concepts/sharpe).

| Tool | Tier | What it answers |
|------|------|-----------------|
| `pulse_sharpe_leaderboard`      | Starter | The 50 most consistent wallets over the last 30 completed UTC days, among wallets with at least $2,500 of stored equity. Refreshed every 30 minutes |
| `pulse_trader_sharpe`           | Starter | One wallet's score over the last 30 completed UTC days, with realized PnL, fill count and the daily mean and standard deviation |
| `pulse_trader_sharpe_interval`  | Starter | The same over a window you choose: `startDay` (within the last 90 days) and `days` (1–90). Out-of-range windows are rejected, not shortened |
| `pulse_trader_sharpe_monthly`   | Starter | Three buckets, newest first: 3 × 30 days, or the current and two previous calendar months with `useCalendarMonths` |

**Sharpe filters on cohort tools.** `live_cohort_bias`, `live_positioning_by_entry`, `pulse_cohort_positions`, `pulse_cohort_trades` and the five `pulse_cohort_recent_*` tools take optional `minRecentSharpe` (30-day score, refreshed hourly) and `minTotalSharpe` (full-history score, refreshed daily). Both are inclusive minimums, combined with AND, applied before limits and aggregation, and use each wallet's **current** score. Each tool keeps its own tier.

## Interactive chart (v0.17.0)

<Note>
  Released 12 Oct 2026 in connector v0.17.0; the sections below cover the chart work from v0.14.0 to v0.17.0. The interactive views appear only in clients that support MCP Apps; text-only clients get the same tool results.
</Note>

### v0.14.0: price charts and bounded candle history

Use **`market_recent_candles`** for a price chart; use `market_price` for a quick mark/index/funding/OI lookup. Candles require **Starter**; the chart's Coinversa layers (entry profile, average entries, Apex vs Crowd history, biggest trades) are **Pro**, and on a Starter key the chart marks them with an upgrade link instead of failing. An MCP Apps client can render candlesticks, dollar volume, moving averages (EMA 21, SMA 20/50), VWAP, Bollinger Bands, RSI, RSI zone markers, MACD and Stochastic. Text-only clients retain the candle result; `indicators` selects the initial chart layers without changing those rows.

| Input or result | Behavior |
|---|---|
| `symbol` | Native or builder-dex ticker, such as `BTC`, `ETH` or `xyz:GOLD` |
| `interval` | `1m` (default), `5m`, `15m`, `1h`, `4h` or `1d` |
| `limit` | Default 240; **maximum 500**. Larger requests are clamped to 500 rather than rejected |
| Candle order | Newest first in the tool result |
| `volume` | **USD notional**. For hourly-source candles, estimated as base quantity × `(high + low + close) / 3` before aggregation |
| Unknown `symbol` | `404` naming the symbol when Hyperliquid's market list confirms it is unlisted; use `list_markets` to find the exact ticker |

The limit bounds the source history too. With the current fallback aggregation, `5m` and `15m` use the latest 500 one-minute bars; `4h` and `1d` use the latest 500 hourly bars. You may therefore receive fewer than 500 aggregated candles. This is recent history, with no older-page cursor.

**Market search** uses `list_markets`: `search` matches the symbol case-insensitively before pagination, and `dex` narrows the venue. For example, search for `gold`, then use the returned `xyz:GOLD` ticker. Inactive listings are hidden unless `includeInactive=true`; the connector's search and paging controls do not add parameters to the underlying API route.

### v0.15.0: explore the chart locally

The chart adds a searchable market picker, remembered selections, synchronized indicator panes, candle readouts, keyboard inspection, pan/zoom, and controls to return to the latest available bars. Search typing, indicator settings and range changes use loaded data. Returning to a cached market/interval reuses its candles; **Refresh** requests candles explicitly and keeps the previous chart visible if the request fails.

Liquidation levels and Apex vs The Crowd positioning load on request and refresh separately from candles. They describe **current snapshots**; each layer identifies its retrieval time and any available source measurement time. Expansion and sending an analysis prompt are available only when the host supports them; otherwise the prompt remains selectable for copying.

**Standard candle VWAP** uses `sum(HLC3 × base quantity) / sum(base quantity)`, where `HLC3 = (high + low + close) / 3`. Intraday intervals reset at the UTC day; daily candles anchor to the first loaded bar. It is available only when the source supplies base quantity for the loaded candles and there is positive volume. If those weights are missing, the chart reports VWAP as unavailable instead of treating USD notional as base quantity. The volume histogram remains in dollars.

### Chart layers (v0.16.0)

The chart now draws what only Coinversa has: where open positions got in, who holds them, and how the two flagship cohorts have moved. Two new tools carry the data, and both are useful without the chart:

| Tool | Tier | What it answers |
|---|---|---|
| `live_positioning_by_entry` | Pro | Where did the money that is open right now get in? Equal-width entry-price bins (`buckets` 1–200, default 60, across `range` 1–100% of the mark, default 30), long vs short and by cohort, plus one row per cohort and side with average entry, average leverage, in-profit / underwater / flat notional and notional within 5% of liquidation. `tierType` is `pnl`, `pnl_recent` (last 30 days of PnL — who is winning now) or `size`. Empty bins are dropped unless `includeEmptyBins` is set (`binsOmitted` says how many). Profit splits and liquidation distance use Hyperliquid's live mark (`markMethod: live_mark`), or the newest stored position mark when the feed is unavailable; `markDivergencePct` shows how far the stored marks are from it, and a note flags more than 1% |
| `live_whale_trades` | Pro | What were the biggest fills? Largest first by USD notional, over `since` up to **24h** (default `6h`), `minNotional` default $1M with a $100K floor, `limit` up to 200 (default 50) — with both counterparties' cohorts and what the fill did to each position. `sourceCount` / `sourceTruncated` are the API's own figures; `count` / `totalCount` / `truncated` describe the rows in this response |

`live_cohort_bias_history` gains `tiers` (up to 8, either vocabulary — not together with `tier`), `format: "layer"` (the API's chart envelope with a −1..1 `netBias`, per-series `hoursPresent` and provenance, returned unpaged), `tierType: "pnl_recent"` and `hours` up to **2160** (90 days). A `format: "layer"` answer can be up to 2,160 points per series — pass `maxResponseTokens` or a shorter `hours` when reading it as text; a shortened answer says so in `_responseLimit`, and partial data should never be read as complete. `format: "layer"` requires `tier` or `tiers`. `tierType: "pnl_recent"` snapshots begin 2026-05-14, so no earlier hours are returned.

All three are snapshots or hourly series with explicit caveats — current open positions are **never history**, whale-trade cohorts are the wallets' **current** labels and the aggressor is unknown, and hourly history may contain reconstructed hours with today's labels, so it is not suitable for backtesting. The [chart layer endpoints](/api-reference/chart-layers) page has the fields and the reasoning.

**In the chart.** Ask for a chart — *"show me the BTC 4h chart"* — and `market_recent_candles` opens the interactive view in clients that support MCP Apps. Under **Layers**, the Coinversa layers sit beside the technical indicators:

| Layer | Source tool | What you see |
|---|---|---|
| Liquidation levels | `live_liquidation_heatmap` | Estimated current liquidation exposure as price bands; hover or tap for values |
| Apex vs Crowd | `live_cohort_bias` | Current long share of open notional for each cohort |
| Entry profile | `live_positioning_by_entry` | Long and short USD exposure by entry price, beside the price axis, with Apex and Crowd highlighted. Can be minimized |
| Average entry lines | `live_positioning_by_entry` | Apex and Crowd average long and short entries, compared with the latest candle close (fees and funding excluded) |
| Apex vs Crowd history | `live_cohort_bias_history` | Hourly long share over the loaded chart window, from one `format: "layer"` call capped at 2,160 hours. Missing hours stay gaps; labelled "possibly reconstructed" |
| Biggest trades | `live_whale_trades` | **Off by default.** One call loads the latest 24h sample — up to 50 fills of $100K or more — and Top 50 / 20 / 5 filter it locally. Split markers show the buy-side and sell-side cohort; who initiated the trade is not known |

With no `indicators` passed, the view opens with RSI, the entry profile, average entry lines and liquidation levels. `indicators` accepts `ema21`, `sma20`, `sma50`, `vwap`, `bollinger`, `rsi`, `macd`, `stochastic`, `rsiMarkers` and the Coinversa layers `liquidations`, `positioning`, `entryProfile`, `averageEntries`, `cohortHistory` and `whaleTrades` to choose the initial layers. A **PnL grouping** selector switches the entry layers and history between all-time and 30-day PnL cohorts; the Apex vs Crowd snapshot and biggest-trade markers always use all-time groups.

Each layer loads once per market and is cached in the view. Refreshing candles does not refresh layers — **Refresh layers** does that explicitly — and there is no polling. Every layer shows its source and as-of time, and **Data & sources** keeps the full coverage notes. What Claude sees about the chart is a concise summary per layer, never raw fills or wallet addresses.

### Image sharing (v0.17.0)

**Share**, beside the price, opens a fullscreen composer. Pick a card — **Chart + inspection** (the chart as you left it, with the selected candle or trade) or **Cohort positioning** (Apex and Crowd long/short shares, open notional, wallet counts, average entries and leverage) — and a format: **X landscape** (1600 × 1200) or **Instagram portrait** (1080 × 1350). Then **Share image** hands the PNG and an editable caption to your device's share sheet where the device supports it, and **Save image** downloads it.

Images are rendered locally in the view: no upload service, no account integration, and nothing is posted automatically. Each card carries its snapshot time and the footer *current positions, not a forecast* and *Market data from Hyperliquid, not investment advice*. Complete coverage notes stay in **Data & sources**.

### When the plan does not include a tool

Every gated tool's description ends with its plan (`Plan: Starter ($29/month) or higher.`). If a key's plan does not include the tool, the result is an ordinary tool result, not a tool error (`isError` is false), shaped like this:

```json
{
  "upgradeRequired": true,
  "tool": "live_cohort_bias",
  "requiredPlan": { "tier": "starter", "name": "Starter", "priceUsdMonthly": 29 },
  "currentPlan": { "tier": "free", "name": "Free" },
  "upgradeUrl": "https://coinversa.ai/developers#pricing",
  "message": "live_cohort_bias needs the Starter plan ($29/month) or higher. …",
  "partialAnswer": {
    "note": "What the Free plan can answer now. …",
    "results": [
      { "tool": "market_price", "why": "current price", "data": { … } },
      { "tool": "live_long_short_ratio", "why": "long/short wallet ratio", "data": { … } }
    ]
  }
}
```

`partialAnswer` is present only when the key's plan includes a tool that answers part of the question. Examples: the current price and long/short ratio for the same coin, the Starter cohort-bias snapshot for a Pro positioning layer, or `book_summary` for a Pro book tool. Agents should state the plan and price, share `upgradeUrl` once, use the partial answer (and say which tool it came from), and not retry the gated tool. Revoked or invalid keys are still reported as errors. On REST, the same denial is the `403` described in [Authentication](/authentication).

| `hip4_perp_position_context`  | Pro | Whether outcome holders have open perp positions on the underlying. |

## L4 order book (v0.12.0)

Four tools over the **order-level** book — every resting order with the wallet behind it — each shaped around a question rather than returning a book to parse yourself. `book_summary` is **Starter**; the other three are **Pro**.

| Tool | Tier | What it answers |
|---|---|---|
| `book_summary` | Starter | How deep and how lopsided is this book right now? Touch prices, spread in bps, and per side the size / order count / distinct-wallet count within 0.5, 1, 2, 5 and 10% of mid — plus near- and far-band imbalance and the age of orders at the touch. |
| `book_stop_map` | Pro | Where are the stops, and how much size fires if price gets there? Every untriggered stop and take-profit bucketed by distance from mid in 0.25% steps, with the reduce-only share and the stop/TP split per bucket. |
| `book_whales` | Pro | Who is sitting on this book, and where? The largest resting orders with wallet, price, size, distance from mid and how long they have rested — plus the biggest wallets per side by total resting size. |
| `book_levels` | Pro | What does the depth ladder look like, with the detail L2 throws away? Top levels per side, each with total size, order count, **distinct wallet count** and the age of its oldest order. |

**The wallet addresses join to the trader tools.** `book_whales` returns addresses that go straight into `pulse_trader_profile` or `pulse_trader_performance` — so "who is holding up this bid, and are they any good" is one follow-up call, not a research project.

<Warning>
  **The coin is CASE-SENSITIVE on these four tools**, unlike every other coin-taking tool. It must be the node's own spelling — `BTC`, `HYPE`, `xyz:GOLD`, `cash:TSLA`, `#28200`. `btc` returns 404 with a hint rather than being normalised, because the rollups are keyed on the node's spelling. Use `list_markets` to discover exact names.

  A correctly spelled coin outside the L4 sweep returns 404 (`BOOK_NOT_COVERED`) on all four tools, and retrying will not help; `data_coverage` lists the covered coins, and `market_orderbook` serves the L2 book. Spot pairs such as `PURR/USDC` are not addressable.
</Warning>

Bounds: `book_stop_map` takes `within_pct` 1–10 (default 10), `book_whales` takes `limit` 1–50 (default 20), `book_levels` takes `depth` 1–100 (default 50). All three are integers — a fraction is rejected before a request is made.

<Note>
  **Snapshot-derived, latest-only.** The gateway re-exports the node's full L4 book on a fixed cadence and the rollups are recomputed per coin, so there is **no history** — one row per coin, replaced each time its block height advances. Every response carries `as_of_height` (the L1 block the answer is true at) and `age_s`; check `age_s` before citing a number. Past the staleness ceiling the routes answer `503` rather than serving a stale book. For the aggregated L2 view with no tier gate, use `market_orderbook`.

  `data_coverage` reports a `book` dataset with coins covered, the latest height and its freshness.
</Note>

For the live order-by-order stream rather than a rollup, see the [`l4Book` websocket feed](/websocket/order-book).

## TP/SL trigger orders (v0.17.3)

Both tools are **Pro**. `book_stop_map` buckets stop and take-profit size by distance from mid; these two tools return the **individual orders** behind it, with the wallet on each. See [TP/SL trigger orders](/concepts/trigger-orders).

| Tool | Tier | What it answers |
|---|---|---|
| `book_triggers` | Pro | Which stop-loss and take-profit orders are waiting on this market, and who placed them? |
| `pulse_trader_trigger_orders` | Pro | Which TP/SL orders does this wallet have pending, across markets or for one `coin`? This exact wallet only, not its sub-accounts; no trader record needed |

They read their **own exchange-wide snapshot** — native perps, builder dexes and HIP-4, independent of the L4 sweep — refreshed roughly every minute, latest only. A snapshot missing or older than 1,200 seconds returns `503`. As with the book tools the coin is **case-sensitive** and not normalized, but an unknown coin returns an empty list rather than a 404, so an empty answer proves nothing. `side` is the order's `B`/`A` (buy/sell), not the position's direction.

Paging: `limit` 1–500 (default 100), `offset` up to 100,000. For any page after the first, pass `snapshot_height` = the first page's `as_of_height`; a `409` means the snapshot changed, so restart at `offset` 0. Each result adds `count`, `hasMore`, `nextOffset` and a `note` with the value to send next.

## Connector-side parameters

Several tools take shaping parameters that the connector applies **after** it fetches the endpoint — the routes themselves take none of them, and you will not find them in the [API reference](/api-reference/introduction) or the OpenAPI spec. Calling the endpoint directly returns the full payload.

| Tool | Endpoint | Connector-side | Sent upstream |
|---|---|---|---|
| `live_risk_overview` | `/live/risk/overview` | `include`, `limit` (10, max 500), `offset` | — |
| `live_coin_risk_snapshot` | `/live/risk/coins/{coin}` | `include`, `limit` (10, max 200), `offset` | `coin` (path) |
| `list_assets` | `/assets` | `search`, `detail`, `limit` (25, max 500), `offset` | `crossMarketOnly` |
| `hip4_questions` | `/hip4/questions` | `status`, `search`, `limit` (25, max 200), `offset` | — |
| `pulse_trader_daily_stats` | `/pulse/trader/{address}/daily` | `startDate`, `endDate`, `limit` (90, max 1000), `offset` | `address` (path) |
| `list_markets` | `/pulse/market-overview` | `search`, `includeInactive`, `limit` (50, max 500), `offset` | `dex` |
| `live_long_short_ratio` | `/live/long-short`, `/live/coins/{coin}/long-short`, `/live/long-short/history` | `limit` (25, max 500), `offset` (global and history forms) | `coin` (path, or query with `hours`), `hours` |
| `live_cohort_bias_history` | `/live/cohort-bias-history/{coin}` | `limit` (100, max 2000), `offset` | `coin` (path), `hours`, `tierType`, `tier`, `tiers`, `format` |

Parenthesised numbers are the default and the maximum. Every capped response carries `totalCount`, `truncated` and a `note` naming the next `offset`, so an agent can page without guessing.

Around twenty **other** tools also take `limit` and `offset`, and those are passed straight through to the route, which pages for itself. The distinction only matters if you are calling the REST API directly: for the tools above, the parameter names in the Connector-side column do not exist on the endpoint.

<Warning>
Some parameters do cross the boundary — `list_assets`'s `crossMarketOnly`, and `live_cohort_bias_history`'s `hours`, `tierType`, `tier`, `tiers` and `format` are real query parameters on their routes. The paging ones are not. A route silently ignores a parameter it does not declare — `GET /assets?limit=3` returns all 415 assets, not 3 — so do not reach for these names when calling the REST API directly.
</Warning>

<Note>
Every tool accepts a `useToonFormat` flag (default `true`) that returns data in compact [TOON format](https://toon-format.dev) — about 50% fewer tokens than JSON for tabular data. Agents typically want this on; set to `false` if you need standard JSON.

Every tool also accepts `maxResponseTokens` (500–30,000; complete array items are removed until the answer fits, disclosed in `_responseLimit`) and `responseTruncation` (`head` or `tail`, for unpaged arrays). Both are applied by the connector.
</Note>
