Every frame is a single JSON object. Client frames carry a `method`; server frames carry a `channel`. The error strings on this page are **exact** — match them verbatim; they will not change.

## Subscribe

The acknowledgement echoes your subscription back and adds a 16-character hex `id` identifying that subscription on this connection.

```json
→ {"method":"subscribe","subscription":{"type":"tradesByCoin","coin":"BTC"}}

← {"channel":"subscriptionResponse","data":{"method":"subscribe","subscription":{"coin":"BTC","type":"tradesByCoin"},"id":"bc0de255be1a5311"}}
```

The `id` is stable: the same type and arguments always hash to the same `id`. On the three fill feeds argument values are matched **case-insensitively** and case-folded before hashing, so `BTC` and `btc` are one subscription. `l4Book`'s `coin` is the exception — it is **case-sensitive**, hashed as sent, and must be the node's own spelling (`BTC`, `xyz:GOLD`, `#28200`); see [Order book (L4)](/websocket/order-book#subscribing).

## Unsubscribe

Send the same subscription object back with `"method":"unsubscribe"`. The acknowledgement carries the **same** `id` the subscribe returned, so you can match the teardown to the setup. The slot frees immediately.

```json
→ {"method":"unsubscribe","subscription":{"type":"tradesByCoin","coin":"BTC"}}

← {"channel":"subscriptionResponse","data":{"method":"unsubscribe","subscription":{"coin":"BTC","type":"tradesByCoin"},"id":"bc0de255be1a5311"}}
```

## Ping

An application-level heartbeat, independent of the protocol-level ping frames your client library may already send. It is the only liveness probe a browser has.

```json
→ {"method":"ping"}

← {"channel":"pong"}
```

## Data frames

`channel` is the subscription type, `seq` is that subscription's counter, and `data` is an array of `[wallet, fill]` pairs — see [feeds and the fill object](/websocket/feeds#data-frames) for the full shape. There is no subscription id on a data frame.

## Order book frames

`l4Book` speaks three frames of its own, all on channel `l4Book` and all carrying the `coin` as you sent it. The full contract — field meanings, the `data` layout, and the client rule — is on [Order book (L4)](/websocket/order-book).

**Snapshot** — exactly one, first, `seq: 0`; `data` is the node's export of the whole book:

```json
← {"channel":"l4Book","coin":"BTC","snapshot":true,"height":100,"time_ms":1757815848097,"seq":0,"data":{"book_orders":[[…],[…]],"untriggered_orders":[…]}}
```

**Update** — one per block after the snapshot, whether or not the block touched the coin; `height` and `prev` chain the blocks, `seq` is `0` on the updates replayed to bridge the snapshot to the live stream:

```json
← {"channel":"l4Book","coin":"BTC","seq":1,"height":103,"prev":102,"time_ms":1757815848325,"partial":false,"data":{"raw_book_diffs":[…],"order_statuses":[…]}}
```

**Book error** — the subscription is gone; reported on the channel itself, not as an `error` frame, so it names the coin:

```json
← {"channel":"l4Book","coin":"BTC","error":"snapshot","reason":"unknown coin"}
← {"channel":"l4Book","coin":"BTC","error":"resync","reason":"updates not contiguous with snapshot"}
```

## Sequence numbers

`seq` counts **per subscription** and increments by one per frame, starting at 1 on every new connection. Anything else between two consecutive frames on the same stream means frames that never arrived; a value at or below the previous one means the counter restarted — a new session, not a gap.

Because a data frame carries no subscription id, key your tracking on what the frame itself identifies: the `channel` plus the coin or wallet of its first fill. Two `tradesByCoin` subscriptions on one connection both arrive on channel `tradesByCoin` with **separate** counters — tracking on the channel alone reports phantom gaps on every alternation. A client holding two subscriptions of the same type that cannot be told apart from the frame (two `tradesByUser` subscriptions where a fill matches both, say) cannot attribute the frame; hold those on separate connections if attribution matters.

There is no replay: a gap is information about what you missed, not something you can request again. The generated [quickstart clients](/websocket/quickstart) implement the tracking above.

On `l4Book`, `seq` keeps this meaning on live updates, but the snapshot and the replayed updates that bridge it to the live stream carry `seq: 0`, and the chain to gate on is the block-level `prev`, not `seq` — see [seq versus prev](/websocket/order-book#seq-versus-prev).

## Errors on an open socket

`{"channel":"error","data":"<string>"}` arrives **on an open socket** and never closes it — the connection keeps serving whatever it was already serving. This is the opposite of a [refused handshake](/websocket/overview#when-the-handshake-is-refused), which ends the connection before it exists.

| `data` | What it means |
|---|---|
| `bad request` | The frame did not parse as JSON. Only a parse failure produces this — a well-formed frame the server cannot act on gets one of the strings below. |
| `unknown method` | `method` is not `subscribe`, `unsubscribe` or `ping`. The retired `{"method":"auth"}` frame lands here: authentication happens on the upgrade, not in a frame. |
| `unknown subscription type` | `type` is not in the catalog. The type is case-sensitive — `tradesByCoin` works, `TRADESBYCOIN` does not — and a subscribe carrying no subscription object at all answers this too. |
| `missing argument <arg>` | A required argument was absent or empty, naming it: `missing argument coin`, `missing argument user`. |
| `too many subscriptions` | This connection is at its subscription cap, or already holds the 8 concurrent `l4Book` subscriptions a connection may hold. The cap counts distinct subscriptions, so a repeat of one you already hold is free; unsubscribe one and the slot frees immediately. |
| `server at subscription capacity` | A service-wide bound on unique subscriptions. Joining a subscription that already exists still works. |
| `feed not in tier` | That subscription type is not included in your tier — the firehose on Free, `l4Book` below Pro. Check `connected.data.limits.feeds`. |

A book subscription that starts and then fails — an unknown coin, a snapshot or replay that could not be fetched, an update chain that would not close onto the snapshot — is reported on the `l4Book` channel itself, not here; see [errors on the book channel](/websocket/order-book#errors-on-the-book-channel).

## Closing

Close the socket from your side with a normal closure (`1000`); the connection is returned to your account's pool at once. A silent disconnect — a laptop lid, a dropped network — holds its slot until keepalive notices, roughly 40 seconds, which is why a fast reconnect after a crash can meet a `429` briefly.
