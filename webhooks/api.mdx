Every route on this page is relative to one base URL and, except `/health`, authenticated:

```text
https://webhook.coinversa.ai
Authorization: Bearer YOUR_API_KEY
```

Subscriptions belong to the **account**, not to a particular key: any of your keys sees and manages all of them, and they share one allowance and one [inbox](/webhooks/inbox). The same operations are in the developer portal's **Webhooks** page and, for inbox subscriptions and reading the inbox, in the [MCP tools](/webhooks/agents#the-tools).

<Note>
This API is served by `webhook.coinversa.ai`, not the data API at `api.coinversa.ai`. It takes `Authorization: Bearer`, not `X-API-Key`, and it is not in the data API's OpenAPI spec. REST auth failures are `403` on the data API; here a missing or invalid key is `401`.
</Note>

## Authentication

One header, the same key as REST and the WebSocket:

```text
Authorization: Bearer <cvsa_ API key>
```

Subscriptions and the inbox belong to the account, not to one key: sibling keys on the same account see and manage the same subscriptions and share the allowance. Connections made through the hosted MCP connector are authenticated for you; nothing to configure.

Missing or invalid credentials, and unknown, revoked or suspended keys, are `401`. An auth-backend outage is `503`, never anonymous access — treat a `503` as *temporarily unavailable* and retry, not as a bad key.

## Summary

Every authenticated row takes the Bearer header above.

| Method | Path | Auth | What it does |
|---|---|---|---|
| `GET` | `/v1/subscriptions/definitions` | yes | The types your plan may create, with `args`, `filters` and `minTier` |
| `POST` | `/v1/subscriptions` | yes | Create a subscription with `deliveryMode` `http` (default, returns the signing secret) or `inbox` (no `url`, no secret) |
| `GET` | `/v1/subscriptions` | yes | List this account's subscriptions with their `deliveryMode` (no secrets) |
| `DELETE` | `/v1/subscriptions` | yes | Delete **all** this account's subscriptions |
| `DELETE` | `/v1/subscriptions/{id}` | yes | Delete one subscription |
| `POST` | `/v1/subscriptions/{id}/enable` | yes | Re-enable a subscription a `410` disabled |
| `GET` | `/v1/subscriptions/{id}/secret` | yes | Read the subscription's signing secret (`400` on an inbox subscription) |
| `GET` | `/v1/inbox` | yes | The account inbox's `state` |
| `GET` | `/v1/inbox/peek` | yes | Read up to `count` pending inbox messages, optionally of one `type`, without deleting them and with no receipt |
| `POST` | `/v1/inbox/drain` | yes | Read up to `count` pending inbox messages within `maxBytes`, oldest first, without deleting them |
| `POST` | `/v1/inbox/ack` | yes | Delete inbox messages by batch prefix or by `inboxIds` |
| `GET` | `/v1/deliveries` | yes | List recent HTTP deliveries with their status, newest first |
| `GET` | `/v1/deliveries/{id}` | yes | One delivery with the exact payload that was sent |
| `POST` | `/v1/deliveries/{id}/resend` | yes | Send a stored delivery again |
| `GET` | `/health` | none | Liveness: `200`, with service counts in the body |

## Definitions

`GET /v1/subscriptions/definitions` → `{ "types": [...], "filterLogic": "and" }`.

Only the types **permitted by your tier** are listed, so Free sees the Free-tier types even though its subscription allowance is zero: feed access and subscription allowance are separate checks. The same declarations drive validation and event field extraction — this is not an arbitrary query interface. Each type carries:

| Field | Meaning |
|---|---|
| `type` | The name you send at creation |
| `args` | Scope and configuration arguments. Each declares `type`, `required`, optional `options` and optional `default`. Wallet arguments also declare `minItems: 1` and `maxItems: 1000`: they take one address or an array — or `maxItems: 1` on the two wallet [liquidation risk types](#liquidation-risk-types), which take exactly one. Three arguments also declare a numeric range: `max` on `priceMovePct`, and `min` and `max` on the integer arguments `buckets` and `range`, which are sent as strings like every other number. Other ranges, such as `points` on `cohortBiasMove`, are enforced at creation without being declared |
| `filters` | Public field names. Each declares `type`, `label`, optional `unit` (`base`, `quote`, `minutes`, `ratio`, `count` or `percent`), `exact`, optional enum `options` and the allowed numeric `operators` |
| `minTier` | The minimum plan, inherited from the underlying feed. `priceCross` also exports `sourceMinTiers` for its `mark` and `trade` sources |

```json
{
  "type": "tradesByUser",
  "args": {"user": {"type": "address", "required": true, "minItems": 1, "maxItems": 1000}},
  "filters": {
    "coin": {"type": "string", "label": "Market", "exact": true},
    "sz": {
      "type": "decimal", "label": "Size", "unit": "base",
      "exact": true, "operators": ["gt", "gte", "lt", "lte"]
    }
  },
  "minTier": "free"
}
```

The example omits the other trade fields for brevity. `minItems` and `maxItems` on `user` mean it accepts one address or an array of 1 to 1,000 ([one wallet or many](#one-wallet-or-many)). Read the endpoint rather than maintaining a client-side list.

## Create a subscription

`POST /v1/subscriptions`

| Body field | Type | Required | Notes |
|---|---|---|---|
| `type` | string | yes | A [subscription type](/webhooks/events): one of the six event types, the four [cohort bias types](/webhooks/cohort-bias) or the four [liquidation risk types](/webhooks/liquidation-types) |
| `args` | object | per type | `user` for the four by-user types — one address or an array of 1 to 1,000 ([below](#one-wallet-or-many)); `coin`, `threshold`, optional `source` and `direction` for `priceCross`; none for `liquidations`; `coin` and, per type, `cohort`, `otherCohort`, `points`, `direction` and `tierType` for the cohort bias types ([below](#cohort-bias-types)); one `user` or a `coin`, with a threshold, for the liquidation risk types ([below](#liquidation-risk-types)). Wallets are normalised to lowercase |
| `filters` | object | no | Exact values or `gt` / `gte` / `lt` / `lte` bounds, AND across fields — see [Filters](/webhooks/events#filters). `priceCross`, `cohortBiasOpposition`, `liquidationRiskCross`, `liquidationExposure` and `liquidationMap` take none |
| `deliveryMode` | string | no | `http` (default) delivers to `url`; `inbox` stores matches in the account [inbox](/webhooks/inbox) instead |
| `url` | string | for `http` | Public HTTPS on port 443. Redirects and private or reserved addresses are refused. **Omit it** on an inbox subscription |

```json
{
  "type": "tradesByUser",
  "args": {"user": "0x0123456789012345678901234567890123456789"},
  "filters": {"coin": "BTC", "sz": {"gt": "1.5", "lte": "10"}},
  "url": "https://example.com/hook"
}
```

`args` selects and configures the source independently of the optional `filters`. The original top-level `user` spelling is still accepted, but do not send `user` both at the top level and inside `args`.

### One wallet or many

On the four by-user types `args.user` is **one address string or an array of 1 to 1,000 addresses**; the definitions advertise `minItems: 1` and `maxItems: 1000` on the argument. The top-level `user` spelling accepts either form too.

```json
{
  "type": "tradesByUser",
  "args": {
    "user": [
      "0x0123456789012345678901234567890123456789",
      "0xabcdefabcdefabcdefabcdefabcdefabcdefabcd"
    ]
  },
  "filters": {"coin": "BTC", "sz": {"gt": "1.5", "lte": "10"}},
  "url": "https://example.com/hook"
}
```

- One array is **one subscription** against your allowance and one underlying processor feed; it does not change the type's minimum plan.
- Addresses are lowercased; arrays are **sorted and deduplicated**. The 1,000 limit is checked before deduplication.
- An **empty array**, an **invalid address** or **more than 1,000 entries** is a `400`. Creation bodies are limited to **64 KiB**.
- In create and list responses a one-element array — including one left after deduplication — is returned as a **string**; the legacy top-level `user` appears only for a single-wallet scope.
- Matching events from every listed wallet in a source block arrive together, in source order, in one delivery's `data`, with the same filters applied to each. Non-wallet arguments stay single-valued.

### Cohort bias types

The four cohort bias types take `coin` and, depending on the type, a cohort, a second cohort, a direction or a number of points. One body per type, with every required argument:

```json
{"type": "cohortBias", "args": {"coin": "BTC"}, "url": "https://example.com/hook"}
```

```json
{"type": "cohortBiasFlip", "args": {"coin": "BTC", "cohort": "apex", "direction": "short"}, "url": "https://example.com/hook"}
```

```json
{"type": "cohortBiasOpposition", "args": {"coin": "BTC", "cohort": "apex", "otherCohort": "crowd"}, "url": "https://example.com/hook"}
```

```json
{"type": "cohortBiasMove", "args": {"coin": "BTC", "cohort": "apex", "points": "10"}, "url": "https://example.com/hook"}
```

- `coin` is required on all four, matched case-insensitively, and can be a qualified symbol such as `xyz:GOLD`.
- `tierType` is optional on all four: `pnl` (default), `size`, `pnl_recent` or `size_recent`. A `cohort` or `otherCohort` must belong to that classification — a cohort from the other one is a `400` — and `cohortBiasOpposition` needs two different cohorts.
- `direction` on `cohortBiasFlip` is `long`, `short` or `both` (default): the side the cohort flips to.
- `points` on `cohortBiasMove` is a positive decimal **string**, at most `200`: percentage points of net bias.
- `cohortBias`, `cohortBiasFlip` and `cohortBiasMove` accept the `netBias`, `longNotional`, `shortNotional` and `accountCount` filters; `cohortBiasOpposition` accepts none.

They are evaluated on stored snapshots, normally taken every 15 minutes, not on each trade. What each one fires on, the cohorts and the delivered rows are on [Cohort bias types](/webhooks/cohort-bias).

### Liquidation risk types

The four liquidation risk types take either one wallet or one market, and a threshold. One body per type, with every required argument:

```json
{"type": "liquidationRiskCross", "args": {"user": "0x0123456789012345678901234567890123456789", "liquidationDistancePct": "5", "direction": "below"}, "url": "https://example.com/hook"}
```

```json
{"type": "liquidationRisk", "args": {"user": "0x0123456789012345678901234567890123456789", "points": "2"}, "url": "https://example.com/hook"}
```

```json
{"type": "liquidationExposure", "args": {"coin": "BTC", "priceMovePct": "3", "minNotional": "6000000"}, "url": "https://example.com/hook"}
```

```json
{"type": "liquidationMap", "args": {"coin": "BTC", "priceChangePct": "1"}, "url": "https://example.com/hook"}
```

- `user` on `liquidationRiskCross` and `liquidationRisk` is **exactly one** wallet — a string or a one-element array. A second address is a `400`. There is no `coin` argument: every open position on record for the wallet is checked.
- `liquidationDistancePct` on `liquidationRiskCross` is a positive decimal **string** in percent (`"5"` is 5%); `direction` is `above`, `below` or `both` (default), and `below` is closer to liquidation.
- `points` on `liquidationRisk` is a positive decimal string — percentage points of distance, with no upper limit. It is the one type of the four that takes a filter: `liquidationDistancePct`.
- `coin` on `liquidationExposure` and `liquidationMap` is matched case-insensitively and can be a qualified symbol such as `xyz:GOLD`.
- `priceMovePct` on `liquidationExposure` is a decimal string above `0` and at most `100`; `minNotional` is a positive decimal string in quote units. `direction` is `down`, `up` or `both` (default). `resetNotional` is optional, positive and at most `minNotional`, and defaults to it.
- `priceChangePct` on `liquidationMap` is a positive decimal string. `buckets` and `range` are optional **integer strings**: `"1"` to `"200"` (default `"50"`) and `"1"` to `"100"` (default `"30"`).

They are evaluated about once a minute on stored positions and liquidation levels, not on each price tick. What each one fires on and the delivered fields are on [Liquidation risk types](/webhooks/liquidation-types).

The response carries the subscription — `type`, the normalised `args`, the saved `filters`, its `id`, `deliveryMode`, `url` and `disabled` status — and, **on creation of an `http` subscription only**, the `whsec_…` signing secret. List responses never include it; read it later with [`GET /v1/subscriptions/{id}/secret`](#read-the-signing-secret).

### Inbox delivery

Send `"deliveryMode": "inbox"` and no `url`, and matching frames are stored in your account's one inbox instead of being POSTed — the same types, `args` and `filters`, one of the same subscription slots, no signing secret, and `403` on Free. Read them with the three inbox routes [below](#inbox). The full contract is on [Inbox delivery](/webhooks/inbox).

```json
{
  "type": "tradesByUser",
  "args": {"user": "0x0123456789012345678901234567890123456789"},
  "filters": {"coin": "BTC"},
  "deliveryMode": "inbox"
}
```

A subscription's configuration is **immutable**: delete and recreate to change it, which also resets `priceCross` crossing state and a cohort bias or liquidation risk subscription's state. If activating the underlying feed fails, creation **rolls back** and answers `503` rather than leaving a saved subscription behind.

Errors: `400` (invalid format, unknown type, argument, filter or operator, impossible range, an empty or over-1,000 `user` array or an invalid address in it, a cohort outside the chosen `tierType`, `points` outside its range, more than one wallet on a liquidation risk type, `priceMovePct` above `100`, `resetNotional` above `minNotional`, `buckets` or `range` that is not an integer string in its range, a body over 64 KiB — checked before anything is saved), `403` (the type is not permitted by your tier, or an inbox subscription on Free), `429` (your account is at its subscription allowance), `503` (auth, storage or feed unavailable).

| Type | `args` | Minimum plan |
|---|---|---|
| `tradesByUser` | required `user`: one address or 1–1,000 | Free (Free's allowance is zero) |
| `twapSliceFillsByUser` | required `user`: one address or 1–1,000 | Free (Free's allowance is zero) |
| `twapStatusesByUser` | required `user`: one address or 1–1,000 | Pro |
| `liquidations` | none | Agent |
| `liquidationsByUser` | required `user`: one address or 1–1,000 | Agent |
| `priceCross` | required `coin`, `threshold`; optional `source`, `direction` | Free for both sources (Free's allowance is zero) |
| `cohortBias` | required `coin`; optional `cohort`, `tierType` | Starter |
| `cohortBiasFlip` | required `coin`, `cohort`; optional `direction`, `tierType` | Starter |
| `cohortBiasOpposition` | required `coin`, `cohort`, `otherCohort`; optional `tierType` | Starter |
| `cohortBiasMove` | required `coin`, `cohort`, `points`; optional `tierType` | Starter |
| `liquidationRiskCross` | required `user` (exactly one wallet), `liquidationDistancePct`; optional `direction` | Starter |
| `liquidationRisk` | required `user` (exactly one wallet), `points` | Starter |
| `liquidationExposure` | required `coin`, `priceMovePct` (above `0`, at most `100`), `minNotional`; optional `direction`, `resetNotional` (at most `minNotional`) | Starter |
| `liquidationMap` | required `coin`, `priceChangePct`; optional `buckets` (integer string, `1`–`200`, default `50`), `range` (integer string, `1`–`100`, default `30`) | Starter |

Tier checks are **creation-time** checks, not continuous re-authorisation of saved subscriptions after an account change.

## List subscriptions

`GET /v1/subscriptions` → this account's subscriptions, each with its `type`, `args`, `filters`, `id`, `deliveryMode` (`"http"` or `"inbox"`), `url` (HTTP subscriptions) and `disabled` status. No secrets.

## Delete a subscription

`DELETE /v1/subscriptions/{id}` deletes one subscription you own. For `priceCross`, the cohort bias types and the liquidation risk types it also removes the stored baseline or state and any pending deliveries in the outbox. Deleting an inbox subscription stops collection but **does not delete the messages it already stored** — acknowledge those on the [inbox](/webhooks/inbox#acknowledge).

## Delete all subscriptions

`DELETE /v1/subscriptions` deletes every subscription on the account.

## Re-enable a subscription


`POST /v1/subscriptions/{id}/enable` re-enables a subscription that a `410` from your URL disabled. It is idempotent. It answers `429` if the account is already at its subscription allowance — a disabled subscription does not count toward it, so enabling one is a creation-time check again.

## Read the signing secret

`GET /v1/subscriptions/{id}/secret` returns the subscription's `whsec_…` signing secret — the one returned at creation. There is one secret per subscription and no rotation; see [Signatures and delivery](/webhooks/signatures#one-secret-per-subscription). An **inbox** subscription has no secret, and this route answers `400` for it.

## Inbox

Four routes read the account's one inbox; the semantics are on [Inbox delivery](/webhooks/inbox).

| Route | Request | Response |
|---|---|---|
| `GET /v1/inbox` | — | `{"state": {pendingMessages, pendingBytes, maxMessages, maxStoredBytes, overflowDroppedTotal, expiredTotal}}` |
| `GET /v1/inbox/peek?type=tradesByUser&count=10&maxBytes=65536` | Same `count` and `maxBytes` as drain; optional `type`, one exact subscription type (`400` if unknown) | `{"messages", "hasMore", "state"}` — oldest matching first, **nothing deleted, no receipt**. `hasMore` counts matching messages only; `state` is account-wide. `413` with `requiredMaxBytes` as for drain |
| `POST /v1/inbox/drain?count=10&maxBytes=65536` | No body. `count` 1–1,000 (default 10); `maxBytes` 1,024–4,194,304 (default 65,536), a budget for the whole response | `{"batchId", "messages", "hasMore", "state"}` — oldest first, **nothing deleted**. `413` with `requiredMaxBytes` when the oldest message does not fit; an empty inbox returns an empty `batchId` |
| `POST /v1/inbox/ack` | **One** of `{"batchId", "count"}` (an absolute prefix of that batch) or `{"inboxIds": [...]}` (1–1,000) | `{"acknowledged", "state"}` — `acknowledged` is what **this** request removed, so a retry returns `0`. Idempotent |

A message is the delivery envelope plus `inboxId` (`msg_` + 32 hex) and `receivedAt` ([the message](/webhooks/inbox#the-message)).

## Delivery history

Every delivery to an **HTTP** subscription is recorded in the account's delivery history, so you can see what was sent, whether your URL took it, and send it again. Inbox subscriptions have no history; their messages are already [stored](/webhooks/inbox). History started on **November 17, 2026**; earlier deliveries are not in it.

History belongs to the **account**: every API key on it sees the same records. It is kept apart from the inbox and does not count against the inbox's allowance, but has the same limits, applied separately: **14 days**, your plan's message count (Starter 1,000, Agent 50,000, Pro and Enterprise 1,000,000, Free 0) and **2 GiB** of compressed payloads, with the oldest evicted first on overflow ([Plan limits](/webhooks/limits#delivery-history)). Nothing deletes a record early: reading it, a successful delivery and a resend leave it in place, and deleting a subscription keeps its history until it expires.

| Route | Request | Response |
|---|---|---|
| `GET /v1/deliveries?count=10&maxBytes=65536` | All optional: `count` 1–1,000 (default 10); `maxBytes` 1,024–4,194,304 (default 65,536), a budget for the whole response; `subscriptionId` to show one subscription, deleted ones included; `cursor`, the `nextCursor` of the previous page | `{"deliveries", "hasMore", "nextCursor", "state"}` — **newest first**, metadata only, no payloads. `413` with `requiredMaxBytes` when the first record does not fit |
| `GET /v1/deliveries/{id}` | No parameters | One record, plus `payload`: the exact JSON body that was POSTed |
| `POST /v1/deliveries/{id}/resend` | No body, no parameters | `202` `{"id", "status": "pending"}` — the resend is queued, not yet delivered |

A record looks like this:

```json
{
  "id": "msg_0123456789abcdef0123456789abcdef",
  "subscriptionId": "sub_0123456789abcdef0123456789abcdef",
  "type": "tradesByUser",
  "url": "https://example.com/hook",
  "receivedAt": "2026-11-17T12:00:00Z",
  "status": "delivered",
  "attempts": 1,
  "lastAttemptAt": "2026-11-17T12:00:01Z",
  "httpStatus": 200
}
```

- `id` is the delivery's `webhook-id` header.
- `status` is `pending` (queued or being sent), `retrying` (waiting for its next attempt, at `nextAttemptAt`), `delivered` (the last attempt got a `2xx`) or `failed`.
- `attempts` counts every attempt. `lastAttemptAt`, `httpStatus` and `error` describe **only the most recent** one; earlier attempts and your URL's response body are not kept.
- A delivery the queue had no room for is recorded as `failed` with `0` attempts. One cut off by a restart of the service is `failed` with a restart error. Both can be resent.
- `state` counts the history itself: `storedMessages`, `storedBytes`, `maxMessages`, `maxStoredBytes` and the cumulative `overflowDroppedTotal` and `expiredTotal`, for the whole account even when you filter by `subscriptionId`.

To page back, pass `nextCursor` unchanged with the same `subscriptionId`; new deliveries arriving meanwhile do not shift it. Times are UTC.

### Resend

A resend POSTs the stored payload again to the subscription's **current** URL, signed with its secret. It keeps the same `webhook-id`, so a receiver that deduplicates on it will drop a resend of a delivery it already accepted; the `webhook-timestamp` and signature are new. Filters are not re-run and nothing about the subscription changes.

`202` means the resend is queued. Read the record again to see whether it arrived. It goes through the normal retry policy and shares the subscription's outbox of **32** pending deliveries. Resending a delivery that is waiting for a retry sends it now instead of adding a second copy.

| Status | Why |
|---|---|
| `404` | Unknown id, another account's id, or a record that expired or was evicted |
| `409` | The delivery is already queued or being sent; the subscription is disabled ([re-enable](#re-enable-a-subscription) it first); or the subscription was deleted |
| `429` | The subscription's outbox already holds 32 pending deliveries |
| `400` | A body or query parameters were sent |

## Health


`GET /health` needs **no key** and answers `200` while the service is up. The body is a JSON object of counts — `subscriptions` (saved subscriptions), `feeds` (active feed subscriptions), `queued` (fresh deliveries waiting), `retrying` (retries waiting) and `outbox` (pending outbox rows). Treat the status code as the health signal and the body as informative: a build may answer `200` with an empty body, so accept both. It does not check auth or feed readiness.

## Delivery semantics

What a delivery looks like is on [Signatures and delivery](/webhooks/signatures). The status codes **your** URL returns mean:

| Your response | Effect |
|---|---|
| Any `2xx` | Acknowledged |
| `410` | The subscription is **disabled** until you call [`/enable`](#re-enable-a-subscription) |
| Anything else | Retried on the bounded policy — up to nine attempts over about 76 hours, respecting `Retry-After` up to 24 hours — then marked `failed` in the [delivery history](#delivery-history), where you can resend it |

## Errors


| Status | Meaning |
|---|---|
| `400` | Invalid format; unknown type, argument, filter or operator; impossible range; an argument outside the range its definition declares (`priceMovePct` above `100`, `buckets` above `200`). Nothing is saved. Also `/secret` on an inbox subscription, bad peek, drain or delivery history parameters, a resend with a body, and a bad or expired ack receipt |
| `401` | Missing or invalid credentials, in either [authentication mode](#authentication) |
| `403` | The source type is not permitted by your account tier (checked at creation); an inbox subscription on Free |
| `404` | A delivery history id that is unknown, another account's, expired or evicted |
| `409` | Resend: the delivery is already queued or being sent, or its subscription is disabled or deleted |
| `413` | Drain, peek or the delivery history list: the first record does not fit `maxBytes`; the body carries `requiredMaxBytes` |
| `429` | The account's subscription allowance is reached — on create and on `/enable`. Disabled subscriptions do not count toward it. Also a resend when the subscription's outbox is full |
| `503` | Auth, storage or feed unavailable. An unknown or missing auth tier fails closed. On create, the subscription was rolled back |

Error bodies are **plain text**, not JSON — `Unauthorized`, `unknown webhook type`, `endpoint must be a public HTTPS URL`, `invalid subscription JSON`, `filter "sz" has an impossible range` — so match on the status code and show the text. The tentative subscription allowances per plan are on [Plan limits](/webhooks/limits).
