An agent connected to the [MCP server](/mcp/setup) can subscribe to events, read what they matched and unsubscribe from chat, with no server and no curl. The eight tools below work on your account's [inbox](/webhooks/inbox): they create and manage **inbox subscriptions** only, act on the same account the portal and REST show, and are bound by the same plan allowance.

<Note>
The MCP tools never take a URL. A subscription created from chat always delivers to the inbox, and the tools neither list nor delete HTTP subscriptions. To have frames POSTed to a URL you own, create the subscription in the [developer portal](https://developers.coinversa.ai) or over [REST](/webhooks/api#create-a-subscription).
</Note>

## Subscribe

`inbox_definitions` lists the types this account's plan can create, with each type's arguments and the filter fields and operators it accepts, so an agent can look them up instead of guessing. It is read-only and paged with `limit` and `offset`.

`inbox_subscribe` takes the same three things a REST create does — a `type`, its `args` and optional `filters` — and always sends `"deliveryMode": "inbox"`. Ask Claude to "watch 0x28f0…9bad's BTC fills of 1.5 or more" and it calls:

```json
{
  "type": "tradesByUser",
  "args": {"user": "0x28f0d2a7c6b3e14f9a8b7c6d5e4f3a2b1c0d9bad"},
  "filters": {"coin": "BTC", "sz": {"gte": "1.5"}}
}
```

- **Types** are the ones on [Subscription types](/webhooks/events): the eight event types `tradesByUser`, `twapSliceFillsByUser`, `twapStatusesByUser`, `liquidations`, `liquidationsByUser`, `leverageUpdatesByUser`, `priceCross` and `liquidityChanged`, and the four [cohort bias types](/webhooks/cohort-bias) `cohortBias`, `cohortBiasFlip`, `cohortBiasOpposition` and `cohortBiasMove`. The four [liquidation risk types](/webhooks/liquidation-types) `liquidationRiskCross`, `liquidationRisk`, `liquidationExposure` and `liquidationMap` are created the same way.
- **`args.user`** on the five by-user types is one address or an array of 1 to 1,000 — one subscription for all of them. `liquidations` takes no args. `priceCross` takes `coin` and a positive decimal-string `threshold`, with optional `source` (`mark` or `trade`) and `direction` (`above`, `below` or `both`). `liquidityChanged` takes `coin`, `side` (`bid` or `ask`), `bandPct` (`"0.5"`, `"1"`, `"2"`, `"5"` or `"10"`), a decimal-string `changePct` and optional `direction` (`up`, `down` or `both`). The cohort bias types take `coin` and, per type, `cohort`, `otherCohort`, `direction`, a decimal-string `points` and optional `tierType`. The two wallet liquidation risk types take **exactly one** `user` with `liquidationDistancePct` or `points`; the two market ones take `coin` with `priceMovePct` and `minNotional`, or `priceChangePct` — every number a string, `buckets` and `range` included ([arguments](/webhooks/liquidation-types#arguments)).
- **`filters`** are AND-combined: exact strings (`coin`, `side`) or `gt` / `gte` / `lt` / `lte` bounds on decimal strings. Numbers are always strings, never JSON numbers. `priceCross`, `liquidityChanged`, `cohortBiasOpposition`, `liquidationRiskCross`, `liquidationExposure` and `liquidationMap` accept no extra filters.

A cohort bias subscription is created the same way. Ask Claude to "tell me when Apex turns net short on BTC" and it calls:

```json
{
  "type": "cohortBiasFlip",
  "args": {"coin": "BTC", "cohort": "apex", "direction": "short"}
}
```

Cohort positioning is a stored snapshot, normally taken every 15 minutes, so the flip reaches the inbox at the next snapshot — not when a trade happens — and the agent sees it the next time it fetches. The message's `data` holds the cohort's row after the flip, with the row before it under `previous` ([`cohortBiasFlip`](/webhooks/cohort-bias#cohortbiasflip)).

The service validates the type, the field names and your plan, exactly as it does for REST: a type above your plan is refused with `403`, as is any subscription on **Free**, and a full allowance with `429` ([Plan limits](/webhooks/limits)). Inbox and HTTP subscriptions share the same slots. The tool returns a compact receipt — `subscribed`, `subscriptionId`, `deliveryMode`, `disabled`, `notifyEvery` — and has no signing secret to show, because an inbox subscription has none.

An optional `notifyEvery` (1–100) groups every N new messages into one notification, so a busy rule hands the agent fewer, larger reads. A group waits for its Nth message with no time limit, and every original message still counts toward the inbox limits ([Notification batching](/webhooks/api#notification-batching)).

A subscription is immutable: to change it, unsubscribe and subscribe again, which resets a price crossing's baseline and a cohort bias or liquidation risk subscription's state. Creation is never retried automatically, so after an ambiguous failure the agent should call `inbox_subscriptions` before trying again rather than risk a duplicate. There is no snapshot and no replay: a subscription collects from the moment it exists. `cohortBias` is the exception — it delivers the current state once when it is created — and `liquidationRiskCross`, `liquidationRisk` and `liquidationExposure` can deliver on their first check if the condition is already met.

## List and unsubscribe

`inbox_subscriptions` lists your inbox subscriptions — id, type, normalized `args`, `filters` and whether each is disabled — sorted by id, `limit` at a time (default 20, at most 100) with `offset`, `hasMore` and `nextOffset` to continue. HTTP subscriptions are left out, so their URLs never reach a chat transcript.

`inbox_unsubscribe` deletes one inbox subscription by its `subscriptionId`. It checks the id is an inbox subscription of yours first and refuses anything else; there is no bulk delete. Unsubscribing stops collection but keeps the messages already stored — they stay pending until acknowledged, expired or evicted.

## Read the inbox

`inbox_state` reports the inbox without touching it: `pendingMessages`, `pendingBytes`, your plan's `maxMessages` and `maxStoredBytes`, and the two cumulative loss counters, `overflowDroppedTotal` and `expiredTotal`.

Reading and deleting are separate steps, as they are over REST: `inbox_peek` and `inbox_fetch` never delete anything, and only `inbox_ack` does. Each message is the delivery envelope — `channel`, `seq`, `subscriptionId`, `data` — plus its `inboxId` and `receivedAt` ([the message](/webhooks/inbox#the-message)). Both read tools take `count` (default 10, up to 1,000) and `maxBytes`, return the oldest messages first, and keep only as many **complete** messages as fit the response budget; a message's `data` is never split.

**`inbox_peek`** looks without consuming. An optional `type` — one exact, case-sensitive event type such as `tradesByUser` or `liquidations`, the envelope's `channel` — narrows it to that type. It returns `messages`, `count`, `hasMore` and the inbox `state` (`stateAt: "peek"`), and no receipt. `hasMore` counts only messages of the requested type; `state` is always account-wide. Peeking does not advance anything, so the same call returns the same messages until they are acknowledged. With `grouped: true` it returns one completed `notifyEvery` group instead, with the `inboxIds` it covers; pass its `notificationId` as `after` to read the next group.

**`inbox_fetch`** reads a batch to process. It is not filtered by type. It returns the same fields plus a **`batchId`**, a receipt for exactly the messages returned (`null` when nothing is returned), with `stateAt: "drain"`.

**`inbox_ack`** deletes. It takes that fetch's `batchId` and a `count`, and deletes the **first `count` messages of that batch** — so after processing, pass the `count` the fetch returned, or fewer if you processed fewer, never the count you asked for. It returns `acknowledged` (what this call removed), `ackStatus` and the `state` after the delete (`stateAt: "ack"`). Repeating the same `batchId` and `count` is safe: it returns `acknowledged: 0` rather than deleting newer messages. A receipt expires after 14 days. To acknowledge exact messages instead — for example the ones a grouped peek returned — pass `inboxIds` (1 to 1,000) in place of `batchId` and `count`.

The loop from chat is therefore **fetch, process, ack** ([the same loop as REST](/webhooks/inbox#for-agents-drain-process-ack)). Three things to know:

- **Messages stay until acknowledged.** A fetch that is never followed by `inbox_ack` leaves its messages pending, and the next fetch returns them again. Before November 16, 2026, the tool was `inbox_drain` and acknowledged what it returned; an agent written for that behaviour now has to call `inbox_ack`. `inbox_drain` still answers as a hidden alias of `inbox_fetch`.
- **`ackStatus: "unconfirmed"`** means the acknowledgement did not come back and the delete may or may not have happened. Retry with the same `batchId` and `count`, and deduplicate by `inboxId`.
- **Two fetches at once** can return the same messages: a fetch does not reserve them. If several agents share an account, give one of them the job.

The inbox is per **account**: a fetch returns what every inbox subscription matched, whichever key or surface created it, and what is acknowledged is gone for the portal and REST too. Messages nobody acknowledges expire after 14 days or are evicted on overflow — see [Limits](/webhooks/inbox#limits).

## The tools

| Tool | Kind | Backing route | What it does |
|---|---|---|---|
| `inbox_definitions` | Read-only | `GET /v1/subscriptions/definitions` | Types available on your plan, with their arguments and filter fields |
| `inbox_subscribe` | Creates a subscription | `POST /v1/subscriptions` | One inbox subscription from `type`, `args`, optional `filters` and optional `notifyEvery`; never a URL |
| `inbox_subscriptions` | Read-only | `GET /v1/subscriptions` | Lists your inbox subscriptions, paged; HTTP subscriptions are excluded |
| `inbox_unsubscribe` | Destructive | `DELETE /v1/subscriptions/{id}` | Deletes one inbox subscription; stored messages are kept |
| `inbox_state` | Read-only | `GET /v1/inbox` | Pending counts, plan capacity and loss counters |
| `inbox_peek` | Read-only | `GET /v1/inbox/peek` | The oldest pending messages, optionally of one type, or one completed group with `grouped`; deletes nothing, no receipt |
| `inbox_fetch` | Read-only | `POST /v1/inbox/drain` | The oldest pending messages and a `batchId` to acknowledge them with; deletes nothing |
| `inbox_ack` | Destructive | `POST /v1/inbox/ack` | Deletes the first `count` messages of a fetched batch, or exact `inboxIds` |

`inbox_subscribe`, `inbox_unsubscribe` and `inbox_ack` are the tools that change anything, and what they change is your Coinversa inbox subscriptions and inbox. The connector still never touches an exchange account, never signs and never trades.

## Hosted connections

The tools work the same however you connected. A connection made with **"Continue with Coinversa"** in Claude, ChatGPT or another client is authenticated for you and resolves the same account, plan and allowance as your API key; a connection made by pasting a key, and the npx package, use that key directly.

## What arrives

Whatever created the subscription and wherever it delivers, the frame is the same: the raw source frame plus `subscriptionId` — stored with an `inboxId` and `receivedAt` in the inbox, signed with [Standard Webhooks](/webhooks/signatures) headers when POSTed to a URL. An agent reading it should treat `data` as the WebSocket [fill objects](/websocket/feeds#the-fill-object) they are — sizes and prices as decimal strings, `side` as `A` (sell) or `B` (buy), `closedPnl` from the node — and say what happened, not what to do about it. On a cohort bias type `data` holds [cohort rows](/webhooks/cohort-bias#the-cohort-row) instead: report the cohort's net bias and the snapshot's time, which is when the snapshot was stored, not when the positioning changed. On a liquidation risk type `data` holds a wallet's positions or a market's exposure ([delivered fields](/webhooks/liquidation-types#delivered-fields)): report it as **potential** exposure from positions as last stored, checked about once a minute — not as a liquidation that happened, and not as a forecast of one. Market data is not advice.

## Roadmap

Today an agent **subscribes** and **pulls** what the subscriptions matched. Having the MCP server push an event into a running session is not something the protocol allows: the version the server speaks has no events capability. The inbox is the pull side of that: a session reads it when it is asked to, not when a fill lands.
