An agent connected to the [MCP server](/mcp/setup) can set up webhook subscriptions, read what they matched and tear them down from chat, without a curl in sight. The five tools below wrap the [webhook API](/webhooks/api) one for one, act on the same subscriptions the portal and REST show, and are bound by the same plan allowance.

<Note>
An agent needs no receiver. `pulse_watch_wallet` creates **inbox** subscriptions by default — matched frames are stored in your account's [inbox](/webhooks/inbox) — and `pulse_events` reads them back from chat. Give it a `url` only if you also run a server that should be POSTed to.
</Note>

## Discover the types first

`pulse_event_types` reads `GET /v1/subscriptions/definitions` — the subscription types **your plan** may create, each with its `args`, its `filters` (field, type, unit, exact or numeric operators) and `minTier`. An agent that calls it before creating a subscription does not have to guess what a filter may say: the same declarations drive validation, so what the tool returns is exactly what a create accepts. See [Subscription types](/webhooks/events).

## Watch a wallet in one call

`pulse_watch_wallet` takes an `address`, optional `coins`, optional `liquidations: true` and an optional `url`. It creates a `tradesByUser` subscription for the wallet's **fills** — one subscription for all its fills, or, with `coins`, one subscription per coin with that coin as the filter. Without a `url` the subscription delivers to the inbox. Ask Claude to "watch 0x28f0…9bad's BTC fills" and it creates the equivalent of:

```json
{
  "type": "tradesByUser",
  "args": {"user": "0x28f0d2a7c6b3e14f9a8b7c6d5e4f3a2b1c0d9bad"},
  "filters": {"coin": "BTC"},
  "deliveryMode": "inbox"
}
```

With a `url`, the same subscription is created as an HTTP subscription instead — `deliveryMode` `http`, delivered to that URL and signed — and the tool sees its signing secret, since creation returns it. If you would rather a secret never pass through a chat transcript, create HTTP subscriptions over [REST](/webhooks/api#create-a-subscription) or in the [developer portal](https://developers.coinversa.ai) and use the tools to list and delete; an inbox subscription has no secret at all.

The tool sets no other filter: `side`, `px`, `sz` and `closedPnl` bounds are set over [REST](/webhooks/api#create-a-subscription) or in the portal. With `liquidations: true`, on **Agent** and above, it also watches the wallet's **liquidations** — one `liquidationsByUser` subscription, a further subscription against your allowance. Each subscription, inbox or HTTP, is one of your plan's slots ([Plan limits](/webhooks/limits)); a type your plan does not include is refused with `403`, as is an inbox subscription on **Free**, a full allowance with `429`, and the tool reports the refusal rather than retrying.

## Read the inbox

`pulse_events` runs the [drain, process, ack](/webhooks/inbox#for-agents-drain-process-ack) loop: it calls `POST /v1/inbox/drain` with a `count` and `maxBytes` sized for a chat turn, hands the messages to the model, and then calls `POST /v1/inbox/ack` for **exactly the messages it exposed** — their `inboxIds`, or the prefix of that drain's batch — so a message the tool had to leave out stays pending for the next call. Each message is the delivery envelope — `channel`, `seq`, `subscriptionId`, `data` — plus its `inboxId` and `receivedAt` ([the message](/webhooks/inbox#the-message)). The inbox's `state` comes back with it, so the agent can say how many messages are still pending and whether `overflowDroppedTotal` or `expiredTotal` moved since the last read.

The inbox is per **account**: `pulse_events` returns what every inbox subscription matched, whichever key or surface created it, and an ack from chat deletes those messages for the portal and REST too. Messages the agent never acknowledges expire after 14 days or are evicted on overflow — see [Limits](/webhooks/inbox#limits).

## List and remove

`pulse_alert_rules` lists your subscriptions — `GET /v1/subscriptions`: type, arguments, filters, delivery mode, URL and whether each is disabled, never the secrets. `pulse_remove_rule` deletes one by its id — `DELETE /v1/subscriptions/{id}`. Subscriptions are immutable, so "watch ETH instead of BTC" is a remove followed by a new watch. Removing an inbox subscription does not delete the messages it already stored.

## The tools

| Tool | Kind | Backing route | What it does |
|---|---|---|---|
| `pulse_event_types` | Read-only | `GET /v1/subscriptions/definitions` | The types your plan may create, with `args`, `filters` and `minTier` |
| `pulse_watch_wallet` | Creates subscriptions | `POST /v1/subscriptions` | `tradesByUser` subscriptions for one wallet, one per coin in `coins`, to the inbox by default or to a `url`; with `liquidations: true` on Agent and above, `liquidationsByUser` as well |
| `pulse_alert_rules` | Read-only | `GET /v1/subscriptions` | Lists your subscriptions |
| `pulse_remove_rule` | Destructive | `DELETE /v1/subscriptions/{id}` | Deletes one subscription |
| `pulse_events` | Reads and acknowledges | `POST /v1/inbox/drain`, `POST /v1/inbox/ack` | Drains pending inbox messages, oldest first, and acknowledges the ones it exposed |

`pulse_watch_wallet`, `pulse_remove_rule` and the ack half of `pulse_events` are the webhook tools that change anything, and what they change is your Coinversa subscriptions and inbox. The connector still never touches an exchange account, never signs and never trades.

## Hosted connections

A user who connected Claude, ChatGPT or another client with **"Continue with Coinversa"** never gave the hosted MCP server a raw `cvsa_` key. For these users the hosted server authenticates to `webhook.coinversa.ai` on their behalf, and the webhook service resolves the same account, plan and allowance a Bearer call would. Nothing changes for you: the tools work the same whichever way you connected. The backend half of that path is still rolling out; until it has, the webhook tools on a hosted connection report the service as temporarily unavailable rather than failing on your key. Connections made by pasting a key, and the npx package, use your key as a Bearer token as before.

## What arrives

Whatever created the subscription and wherever it delivers, the frame is the same: the raw source frame plus `subscriptionId` — signed with [Standard Webhooks](/webhooks/signatures) headers when POSTed to a URL, stored with an `inboxId` and `receivedAt` when it goes to the inbox. An agent reading either should treat `data` as the WebSocket [fill objects](/websocket/feeds#the-fill-object) they are — sizes and prices as decimal strings, `side` as `A` (sell) or `B` (buy), `closedPnl` from the node — and say what happened, not what to do about it. Market data is not advice.

## Roadmap

Today an agent **sets up** subscriptions and **pulls** what they matched. Having the MCP server push an event into a running session is not something the protocol allows: the version the server speaks has no events capability. The inbox is the pull side of that: a session reads it when it is asked to, not when a fill lands.
