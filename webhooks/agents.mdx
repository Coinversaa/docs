An agent connected to the [MCP server](/mcp/setup) can set up and tear down webhook subscriptions from chat, without a curl in sight. The five tools below wrap the [webhook API](/webhooks/api) one for one, act on the same subscriptions the portal and REST show, and are bound by the same plan allowance.

<Note>
A webhook subscription delivers to a **URL**, so the agent still needs a receiver to point at — yours, or a catch hook on Zapier, Make or n8n. An inbox of matched events that an agent reads back from chat, with no receiver at all, is in development: until it is available, `pulse_events` returns a clear error saying so, and `pulse_watch_wallet` needs a `url`.
</Note>

## Discover the types first

`pulse_event_types` reads `GET /v1/subscriptions/definitions` — the subscription types **your plan** may create, each with its `args`, its `filters` (field, type, unit, exact or numeric operators) and `minTier`. An agent that calls it before creating a subscription does not have to guess what a filter may say: the same declarations drive validation, so what the tool returns is exactly what a create accepts. See [Subscription types](/webhooks/events).

## Watch a wallet in one call

`pulse_watch_wallet` takes an `address`, optional `coins`, optional `liquidations: true` and the `url` to deliver to. It creates a `tradesByUser` subscription for the wallet's **fills** — one subscription for all its fills, or, with `coins`, one subscription per coin with that coin as the filter. Ask Claude to "send 0x28f0…9bad's BTC fills to my hook" and it creates the equivalent of:

```json
{
  "type": "tradesByUser",
  "args": {"user": "0x28f0d2a7c6b3e14f9a8b7c6d5e4f3a2b1c0d9bad"},
  "filters": {"coin": "BTC"},
  "url": "https://example.com/hooks/coinversa"
}
```

The tool sets no other filter: `side`, `px`, `sz` and `closedPnl` bounds are set over [REST](/webhooks/api#create-a-subscription) or in the portal. With `liquidations: true`, on **Agent** and above, it also watches the wallet's **liquidations** — one `liquidationsByUser` subscription, a further subscription against your allowance. Each subscription is one of your plan's slots ([Plan limits](/webhooks/limits)); a type your plan does not include is refused with `403`, a full allowance with `429`, and the tool reports the refusal rather than retrying.

Creation returns each subscription's **signing secret**, so a tool that creates a subscription sees it. If you would rather a secret never pass through a chat transcript, create the subscription over [REST](/webhooks/api#create-a-subscription) or in the [developer portal](https://developers.coinversa.ai) and use the tools to list and delete; the secret is also readable later with `GET /v1/subscriptions/{id}/secret`.

## List and remove

`pulse_alert_rules` lists your subscriptions — `GET /v1/subscriptions`: type, arguments, filters, URL and whether each is disabled, never the secrets. `pulse_remove_rule` deletes one by its id — `DELETE /v1/subscriptions/{id}`. Subscriptions are immutable, so "watch ETH instead of BTC" is a remove followed by a new watch.

## The tools

| Tool | Kind | Backing route | What it does |
|---|---|---|---|
| `pulse_event_types` | Read-only | `GET /v1/subscriptions/definitions` | The types your plan may create, with `args`, `filters` and `minTier` |
| `pulse_watch_wallet` | Creates subscriptions | `POST /v1/subscriptions` | `tradesByUser` subscriptions for one wallet to a URL, one per coin in `coins`; with `liquidations: true` on Agent and above, `liquidationsByUser` as well |
| `pulse_alert_rules` | Read-only | `GET /v1/subscriptions` | Lists your subscriptions |
| `pulse_remove_rule` | Destructive | `DELETE /v1/subscriptions/{id}` | Deletes one subscription |
| `pulse_events` | Read-only | `GET /v1/events` | Reads matched events from the inbox, oldest first, with a `since` cursor; today it returns a clear error (see the note above) |

`pulse_watch_wallet` and `pulse_remove_rule` are the only webhook tools that change anything, and what they change is your Coinversa subscriptions. The connector still never touches an exchange account, never signs and never trades.

## What the receiver gets

Whatever created the subscription, the receiver gets the same thing: the raw source frame plus `subscriptionId`, signed with [Standard Webhooks](/webhooks/signatures) headers. An agent that reads a receiver's log should treat `data` as the WebSocket [fill objects](/websocket/feeds#the-fill-object) they are — sizes and prices as decimal strings, `side` as `A` (sell) or `B` (buy), `closedPnl` from the node — and say what happened, not what to do about it. Market data is not advice.

## Roadmap

Today an agent **sets up** webhooks and a server **receives** them. Having the MCP server push an event into a running session is not something the protocol allows: the version the server speaks has no events capability.
